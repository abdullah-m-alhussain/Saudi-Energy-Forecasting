# Reproducibility Guide

## Overview

This repository has been designed as a reproducible research framework.

All stages of the forecasting workflow are organized into independent components, allowing researchers to reproduce the complete experimental pipeline from raw data preparation to final forecasting results.

The project follows a sequential notebook-based workflow to ensure that every processing step can be independently verified.

---

# Repository Organization

The repository is organized into the following major components:

- `benchmarks/`
- `saudi_case_study/`
- `docs/`

The benchmark experiments and the Saudi case study are independent but follow similar methodological principles.

---

# Software Environment

The recommended software environment is:

- Python 3
- Conda (recommended)
- Jupyter Lab or Jupyter Notebook

Project dependencies are provided in the repository environment configuration.

Create and activate the environment from the repository root:

```bash
conda env create -f environment.yml
conda activate saudi-energy-forecasting
```

---

# General Workflow

The complete forecasting workflow follows these stages:

1. Create and activate the Python environment.
2. Obtain any required external benchmark data.
3. Change to the relevant `notebooks/` directory.
4. Launch Jupyter Lab or Jupyter Notebook.
5. Execute the documented notebook workflow.
6. Review generated models, results, and figures.

Each notebook is intended to complete successfully before proceeding to the next stage.

---

# Saudi Case Study Workflow

From the repository root, start the Saudi workflow with:

```bash
cd saudi_case_study/notebooks
jupyter lab
```

Execute the Saudi case study in the following order:

1. `00_Project_and_Data_Inventory.ipynb`
2. `01_Data_Quality_and_Source_Audit.ipynb`
3. `02_Saudi_Household_Data_Integration_and_Validation.ipynb`
4. `03_Exploratory_Data_Analysis.ipynb`
5. `04_Feature_Engineering.ipynb`
6. `05_Model_Preparation_and_Baselines.ipynb`
7. `06_ARIMA_Model.ipynb`
8. `07_Random_Forest_Model.ipynb`
9. `08_XGBoost_Model.ipynb`
10. `09_Hybrid_Model.ipynb`
11. `10_Model_Evaluation_and_Comparison.ipynb`
12. `11_Final_Forecasts_and_Visualizations.ipynb`

Running notebooks in a different order is not recommended because later stages depend on outputs generated by earlier stages.

# Benchmark Workflow

Each benchmark is implemented as one self-contained notebook. First follow
`benchmarks/DATA_ACQUISITION.md`, then launch the corresponding notebook from its
own `notebooks/` directory:

```bash
cd benchmarks/PJM/notebooks
jupyter lab PJM_Benchmark.ipynb
```

```bash
cd benchmarks/Spain/notebooks
jupyter lab Spain_Benchmark.ipynb
```

```bash
cd benchmarks/UCI_Household/notebooks
jupyter lab UCI_Benchmark.ipynb
```

Run each command from the repository root in a separate shell session. Each notebook
performs preprocessing, feature engineering, model training, evaluation, artifact
saving, and visualization for that benchmark.

---

# Generated Outputs

Executing the notebooks produces several categories of outputs, including:

- processed datasets,
- engineered features,
- trained models,
- forecasting predictions,
- evaluation metrics,
- publication-ready figures,
- summary tables.

These outputs are stored within their corresponding project directories. Large
benchmark inputs and generated artifacts are excluded according to `.gitignore`,
while lightweight benchmark evidence is retained. The Saudi case-study artifacts
currently present in the repository are retained as its research record.

---

# Reproducibility Principles

The framework follows several reproducibility principles:

- modular project organization,
- documented preprocessing,
- transparent feature engineering,
- consistent evaluation methodology,
- reproducible forecasting pipeline,
- version-controlled source code.

These principles help ensure that experimental results can be independently verified.

---

# Notes

Researchers extending this framework are encouraged to:

- preserve the notebook execution order,
- document any preprocessing changes,
- maintain consistent evaluation procedures,
- record software dependency updates.

Following these practices improves comparability between future experiments and the original implementation.

---

# Future Extensions

The framework has been intentionally designed to support future additions, including:

- new benchmark datasets,
- additional forecasting algorithms,
- extended Saudi datasets,
- new explanatory variables,
- alternative evaluation strategies.

These extensions can be incorporated without altering the overall project architecture.
